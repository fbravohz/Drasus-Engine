> 🔶 **Extendido por ADR-0141** — añade las reglas de modelado concretas (tipos de columna, STRICT, convenciones, configuración del pool) a la arquitectura de motores definida aquí.
> 🔶 **Enmendado por ADR-0143** — la "Soberanía Total de Datos" de este ADR aplica al Plano de Ejecución (hardware del usuario). A partir de ADR-0143 existe además una Cabina de Mando Central del proveedor que ingiere telemetría/artefactos según el tier del usuario. Zero-Docker y la persistencia embebida local **no cambian**; lo que cambia es que el dato deja de ser inaccesible al proveedor por principio.

### **ADR-0030: Persistencia Soberana "Zero-Docker"**

*   **Decisión:** Prohibir el uso de dependencias de red pesadas o bases de datos externas (Redis, ClickHouse, Docker) en la arquitectura base. Toda la persistencia y analítica se realiza mediante motores embebidos (SQLite, DuckDB) y archivos planos (Parquet).
*   **Objetivo:** Garantizar la **Soberanía Total de Datos** y simplificar el despliegue a una instalación de "un solo clic" (Client Zero Protocol).
*   **Estrategia de Datos (Despliegue Local):**
    * **OLTP (SQLite):** Todo el estado transaccional, libro de órdenes, estados de la app y un **Almacén de Eventos (Event Store)** inmutable para auditoría se maneja en SQLite (Modo WAL).
    * **OLAP (DuckDB + Parquet):** Los datos históricos masivos y resultados de investigación se almacenan en archivos Parquet (**Particionado Hive-Style**) y se consultan vía DuckDB (Out-of-Core).
    * **Excepción (SaaSCloudEngine):** El uso de contenedores (Docker/Podman) se permite estrictamente en la fase de Despliegue Headless para VPS masivo, pero NUNCA será un requisito para el usuario que instale el software localmente en su laptop.
*   **Ventaja:** Portabilidad absoluta de datos; el usuario es dueño físico de su historial sin cuotas de nube ni mantenimiento de servidores.
*   **Costo:** Mayor responsabilidad en los backups locales por parte del usuario.
*   **Alternativas evaluadas y descartadas (revisión 2026-07-24):** ante la duda de si Parquet/Hive-Style/DuckDB eran una elección heredada de un ecosistema Python que ya no aplica, se auditó explícitamente. **Parquet y el particionado Hive-Style no son tecnología de Python** — Parquet es un formato binario columnar agnóstico de lenguaje (spec Apache, leído/escrito nativamente por Rust vía `arrow-rs`) y Hive-Style es una convención de nombres de carpeta, no un motor. **DuckDB tampoco es residuo de Python** — es un motor embebido en C++ con binding Rust maduro (`duckdb-rs`), el mismo patrón que SQLite (C, `rusqlite`) ya validado como pieza central del OLTP. Se evaluó **Delta Lake/`delta-rs`** (100% Rust nativo, log de transacciones ACID, `MERGE`/`UPSERT` y time-travel de fábrica) como reemplazo del mecanismo de reescritura atómica de partición diseñado a mano en ADR-0163 — se **descartó**: Delta Lake resuelve concurrencia multi-writer sobre un lago compartido, y esta arquitectura es local-first single-writer (un solo proceso Rust del usuario escribe su propio Parquet); adoptarlo añadiría complejidad operacional (compactación periódica, `VACUUM`, log de transacciones creciente) sin nadie de ops detrás del usuario para gestionarla, a cambio de resolver una concurrencia que no existe en este diseño. Se revisita si el sistema pasa a multi-writer real (ej. varios nodos VPS escribiendo al mismo dataset compartido, ADR-0119).
*   **Trazabilidad:** [duckdb-sql-engine.md](../features/duckdb-sql-engine.md).
*   **Resultado:** Infraestructura privada de grado institucional comprimida en una arquitectura local persistente.
